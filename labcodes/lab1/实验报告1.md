## 一、实验目的

1. 理解从处理器复位、固件初始化到内核开始执行的启动过程，区分各阶段的职责。
2. 理解链接脚本如何安排内核入口和各数据段，掌握交叉编译、链接及镜像生成的基本过程。
3. 理解汇编入口如何建立栈环境，以及 C 语言内核如何清零 `.bss` 并开始执行。

5. 使用 QEMU 和 GDB，通过指令、内存及寄存器的实际变化验证启动流程。

## 三、实验整体逻辑分析

### 3.1 本章节的逻辑主线

本章围绕“如何让一个最小内核获得处理器控制权并产生可观察的输出”展开。内核运行时不能直接依赖已有操作系统的进程加载器、标准 C 库和运行时初始化，因此必须明确自己的地址布局、入口、栈和基础输出接口。

从构建角度看，源代码先被交叉编译为 RISC-V 目标文件，再按照链接脚本组织成 ELF 内核，随后转换为原始二进制镜像。QEMU 准备固件和内核镜像，使处理器从复位入口开始执行。

从执行角度看，本次观察到的顺序为：复位代码 `0x1000` → OpenSBI `0x80000000` → 内核入口 `0x80200000` → 建立内核栈 → `kern_init` 清零 `.bss` → 格式化输出启动信息 → 无限循环。OpenSBI 初始化细节没有逐条完整跟踪，而是通过阶段入口、参数和断点验证控制权交接。

需要区分“镜像已加载到内存”和“处理器开始执行镜像”两件事。在本次 QEMU 配置中，镜像在虚拟 CPU 开始运行前由 QEMU 装入内存；OpenSBI 负责固件初始化及向内核交接。因而不能将命中内核入口断点描述为捕获了 OpenSBI 从磁盘搬运内核的瞬间。

### 3.2 功能的逐步实现

教材先介绍 OpenSBI、ELF 和 BIN，明确固件与内核如何衔接；再通过链接脚本设置内存布局和入口，使镜像的放置地址与程序预期一致。接着在汇编入口建立栈，转入 C 语言初始化函数。随后从 SBI 字符输出接口逐层封装，得到内核自己的 `cprintf`。最后借助 Makefile 构建运行，并通过 GDB 验证启动过程。

这一顺序体现了功能依赖：没有正确布局就无法可靠进入内核；没有栈环境就无法可靠调用 C 函数；没有基础输出接口就难以观察初始化结果。GDB 则提供了输出之外的验证手段，即使程序尚未具备打印能力，也能检查执行位置和寄存器状态。

### 功能模块一：编译、链接和内存布局

**负责人：** 待补充。

`Makefile` 使用 `riscv64-unknown-elf-` 工具链编译 C 和汇编代码。`-nostdinc` 使源码使用项目提供的头文件，`-fno-builtin` 避免依赖编译器默认内建函数行为；链接使用 `-nostdlib`，不引入宿主系统的标准运行库。`-g` 保留调试信息，便于 GDB 将地址关联到源文件和符号。

链接命令通过 `-T tools/kernel.ld` 指定布局，生成 `bin/kernel`。该 ELF 文件携带用于调试的符号等信息；`objcopy --strip-all -O binary` 再生成 `bin/ucore.img`，供 QEMU 加载。原始 BIN 镜像本身没有 ELF 文件头及段表，加载地址由启动配置给出；不能认为它一定自带说明加载地址的文件头。

`tools/kernel.ld` 指定 `OUTPUT_ARCH(riscv)`、`ENTRY(kern_entry)` 和 `BASE_ADDRESS = 0x80200000`，安排 `.text`、`.rodata`、`.data`、`.sdata`、`.bss` 等段。`.text` 保存代码，`.rodata` 保存只读数据，`.data/.sdata` 保存已初始化的可写数据，`.bss` 保存应初始化为零的数据。

`ALIGN(0x1000)` 将位置计数器推进到 4096 字节边界；这里是地址布局对齐，并不代表已经建立页表。`edata` 标记初始化数据结束的位置，`end` 标记 `.bss` 结束的位置，供 C 代码清零使用。本次反汇编确认入口实际位于 `0x80200000`；ELF 的入口声明和镜像起始位置需要配合，不能只设置入口符号而忽略二进制布局。

### 功能模块二：汇编入口与 C 初始化

**负责人：** 待补充。

涉及入口符号 `kern_entry` 和核心函数：

```c
int kern_init(void) __attribute__((noreturn));
void *memset(void *s, char c, size_t n);
```

`entry.S` 在数据段中用 `.space KSTACKSIZE` 预留栈空间，以 `bootstack` 和 `bootstacktop` 标记其边界。`PGSIZE=4096`，`KSTACKPAGE=2`，因此栈大小为 8192 字节。入口把 `sp` 设为高地址边界，随后尾调用 `kern_init`。

`kern_init` 首先执行 `memset(edata, 0, end - edata)`，建立零初始化数据的初始状态。这里的地址符号由链接器提供，`memset` 由项目自己的 `libs/string.c` 实现。随后调用 `cprintf` 打印启动字符串，最后执行 `while (1)`。`noreturn` 表达该函数不会返回的约定，真正使其不返回的是代码中的无限循环。

### 功能模块三：从 SBI 到格式化输出

**负责人：** 待补充。

核心函数包括：

```c
int cprintf(const char *fmt, ...);
int vcprintf(const char *fmt, va_list ap);
void vprintfmt(void (*putch)(int, void *), void *putdat,
              const char *fmt, va_list ap);
static void cputch(int c, int *cnt);
void cons_putc(int c);
void sbi_console_putchar(unsigned char ch);
uint64_t sbi_call(uint64_t sbi_type, uint64_t arg0,
                  uint64_t arg1, uint64_t arg2);
```

实际调用链是 `cprintf → vcprintf → vprintfmt → cputch → cons_putc → sbi_console_putchar → sbi_call`。

`cprintf` 用 `va_start`、`va_end` 管理变长参数，交给 `vcprintf` 处理；`vcprintf` 初始化字符计数器，并向格式化函数提供输出回调。`vprintfmt` 解析格式字符串，处理字符串、整数等转换，并通过回调逐字符输出；整数转换由 `printnum` 等辅助函数完成。`cputch` 输出字符并累加计数，`cons_putc` 连接通用控制台接口与 SBI 实现。

`sbi_console_putchar` 使用服务编号 1，最终由 `sbi_call` 的内联汇编把编号放入 `a7/x17`，把参数放入 `a0/x10`、`a1/x11`、`a2/x12`，执行 `ecall`，再从 `a0` 获取返回值。这是实验源码采用的传统 SBI 调用接口，不能直接推广为所有新版本扩展的调用格式。

内核运行在 S 模式，通过异常进入 M 模式的 OpenSBI 请求基础服务。它与普通 `call` 的区别是跨越了特权级边界。本次验证了启动字符串的输出，没有遍历测试 `printfmt.c` 支持的全部格式，也没有验证键盘输入、定时器或中断功能。

### 练习一：理解内核启动中的程序入口操作

**负责人：** 待补充。

#### `la sp, bootstacktop` 的操作与目的

`la` 是加载地址的伪指令，将标签 `bootstacktop` 的地址写入栈指针，而不是读取该地址中的数据。栈空间已经由 `.space` 预留，这条指令负责选择栈的位置。栈向低地址增长，所以空栈初始指针应放在高地址边界。

这样做是为了建立内核自己的 C 函数执行环境，支持函数调用中的栈帧、寄存器保存及局部数据存放。进入内核前的 `sp` 指向固件使用的区域，不能将其作为内核自身的栈长期使用。

实际观测为：`bootstack=0x80201000`，`bootstacktop=0x80203000`，两者相差 8192 字节。入口执行前，`sp=0x80046eb0`。本次伪指令展开为：

```asm
0x80200000: auipc sp,0x3
0x80200004: mv    sp,sp
```

第一条计算 `0x80200000 + (0x3 << 12) = 0x80203000`；第二条显示为 `mv sp,sp`，在本次结果中低位补偿为零。分别执行两次 `si` 后，`pc=0x80200008`，`sp=0x80203000`，与栈顶标签一致。这种具体展开取决于汇编和链接结果，不应假定所有地址下都会生成完全相同的指令。

GDB 将该栈顶地址显示为 `<SBI_CONSOLE_PUTCHAR>`，是因为栈顶边界与后续变量共享地址标签位置，不意味着栈指针设置错误；地址与 `&bootstacktop` 相等才是这里的验证依据。

#### `tail kern_init` 的操作与目的

`tail` 是尾调用伪指令，将控制流跳转到 `kern_init`，不为本次跳转写入新的返回地址。`kern_init` 最终进入无限循环，无需返回汇编入口，因此采用尾调用。

本次链接后的指令为：

```asm
0x80200008: j 0x8020000a <kern_init>
```

跳转前 `ra=0x8000ae9a`；执行 `si` 后，`pc=0x8020000a`，`sp=0x80203000`，`ra` 仍为 `0x8000ae9a`。这直接验证了控制流进入 C 函数且没有更新返回地址。保留的旧 `ra` 不代表该函数应当返回 OpenSBI。

### 练习二：使用 GDB 验证启动流程

**负责人：** 待补充。

#### 调试准备

在两个终端进入同一虚拟机源码目录，分别运行 `make debug` 和 `make gdb`。QEMU 使用 `-S` 在 CPU 执行前暂停，使用 `-s` 提供默认 1234 端口的 GDB 服务。GDB 加载 `bin/kernel`，设置 `riscv:rv64` 架构，再连接 `localhost:1234`。ELF 文件在这里用于调试符号，不等于 GDB 把内核重新加载进了虚拟机。

#### 复位入口及最初指令

连接后，`info registers pc sp` 显示 `pc=0x1000`、`sp=0`。执行 `x/6i $pc` 得到：

```asm
0x1000: auipc t0,0x0
0x1004: addi  a2,t0,40
0x1008: csrr  a0,mhartid
0x100c: ld    a1,32(t0)
0x1010: ld    t0,24(t0)
0x1014: jr    t0
```

这些指令位于 QEMU `virt` 的 MROM 复位入口，尚不是 OpenSBI 正文。`auipc` 将当前地址 `0x1000` 放入 `t0`；`addi` 将 `a2` 设为 `0x1028`，指向传给固件的启动信息；`csrr` 读取硬件线程编号到 `a0`；两条 `ld` 分别读取设备树地址和固件入口；最后 `jr` 转移控制权。这里的 40、32 和 24 都是十进制字节偏移。

执行 `x/2gx 0x1018` 得到两个 64 位数值：

```text
0x1018: 0x0000000080000000  0x0000000087e00000
```

执行 `si 5` 后，`pc=0x1014`、`t0=0x80000000`、`a0=0`、`a1=0x87e00000`、`a2=0x1028`。这说明固件入口和启动参数已经准备好，当前停在尚未执行的 `jr t0`。

#### 进入 OpenSBI

再执行一次 `si`，`pc` 变为 `0x80000000`，验证复位代码跳转至 OpenSBI。反汇编显示：

```asm
0x80000000: add s0,a0,zero
0x80000004: add s1,a1,zero
0x80000008: add s2,a2,zero
0x8000000c: jal 0x80000580
```

前三条保存输入参数，第四条调用后续初始化代码。之后没有继续对全部固件指令单步，而是设置内核入口断点，验证其完成初始化后的交接结果。

#### 启动失败与兼容调整

首次设置 `b *0x80200000` 并执行 `continue` 后，一直未命中断点。QEMU 输出显示 `Domain0 Next Address` 为 `0x0`。中断调试时停在 OpenSBI 地址 `0x80003a58`。结合本实验配置，问题是原 Makefile 使用 `-device loader` 放置镜像，但在当前启动方式下未向默认固件提供正确的下一阶段入口。

退出 GDB 和 QEMU 后，在虚拟机中备份 Makefile，将 `qemu`、`debug` 目标中的镜像加载选项改为 `-kernel $(UCOREIMG)`，保留 `debug` 的 `-s -S` 和必要的续行反斜杠。调整后的目标可概括为：

```makefile
qemu: $(UCOREIMG) $(SWAPIMG) $(SFSIMG)
	$(V)$(QEMU) -machine virt -nographic -bios default -kernel $(UCOREIMG)

debug: $(UCOREIMG) $(SWAPIMG) $(SFSIMG)
	$(V)$(QEMU) -machine virt -nographic -bios default -kernel $(UCOREIMG) -s -S
```

上述片段记录虚拟机实际采用的兼容方案；本机原始 Makefile 仍保留压缩包配置。重新启动后，QEMU 显示 `Domain0 Next Address=0x80200000`，同一个入口断点成功命中。这表明此次等待源于启动配置，而不是 GDB 自身失去响应。

![首次启动的下一阶段入口为零](./images/boot-next-address-zero.png)

#### 内核入口、栈初始化与最终运行

第二次调试执行 `b *0x80200000`、`continue`，命中 `kern_entry`，停在 `entry.S` 第 7 行。`pc=0x80200000`，说明 CPU 已到达内核第一条指令，断点时该指令尚未执行。随后使用 `si` 完成练习一的栈初始化和尾调用验证。

进入 `kern_init` 后继续运行，QEMU 输出 `(THU.CST) os is loading ...`。按 `Ctrl+C` 暂停，GDB 定位到 `init.c` 的 `while (1)`，当前指令为：

```asm
0x8020003a <kern_init+48>: j 0x8020003a <kern_init+48>
```

它跳回自身，验证最终无限循环。反汇编后续显示的 `cputch` 位于相邻地址，不会由该循环顺序执行。

#### 问题答案

在本次 QEMU 模拟的 RISC-V 平台上，加电后最初执行的指令位于 `0x1000` 起始的复位代码区域。其主要功能是准备启动参数、获取硬件线程编号、读取设备树和固件入口地址，再跳转至 `0x80000000` 的 OpenSBI。OpenSBI 完成初始化后将控制权交给 `0x80200000` 的内核。`0x1000` 是本模拟平台的选择，不是所有 RISC-V 硬件统一规定的复位地址。

教材提示的 `watch *0x80200000` 本次未使用。由于 QEMU 在 CPU 执行前装入镜像，不能预期该观察点一定捕获运行中的写入；本实验采用阶段单步和入口断点验证执行流程。

### 最终提示词与实际迭代过程

本次没有通过多轮提示词生成内核函数，因此不填写虚构的代码生成次数。实际使用的关键提示词为“手把手带我做练习一和练习二”，并在过程中提供命令输出和截图；启动异常时反馈“现在 gdb 卡住了”。

## 六、实验总结与收获

### 6.1 实验知识与 OS 原理的联系和差异

**系统引导与控制权交接。** OS 原理介绍固件、引导程序与内核分阶段建立运行环境。本实验通过三个实际地址观察了这种交接：复位代码准备参数，OpenSBI 初始化固件环境，内核建立自身运行环境。真实系统可能包含磁盘驱动、镜像校验和复杂引导程序，本次 QEMU 提前装入镜像，不能据此认为所有系统都采用相同加载方式。

**程序内存布局与装载。** OS 原理中的程序装载，需要将代码和数据映射到正确位置。本实验用链接脚本确定各段及入口，以固定加载地址与镜像布局建立契约。链接阶段的地址安排与运行时装载相互配合，但链接器不是内存管理器；本次也没有建立虚拟地址映射或按需调页。原始 BIN 通常不包含 `.bss` 的实际零数据，零初始化由本实验启动代码明确完成，不能认为所有声明的零数据都必须占据镜像中的对应字节。

**内核栈与执行上下文。** OS 原理强调栈保存函数调用信息和局部状态。本实验通过 `sp` 的切换，验证 C 函数执行依赖栈环境。当前只有启动阶段的内核栈，还没有为不同进程建立独立内核栈，也没有上下文切换。栈空间大小和页对齐是静态布局安排，不能等同于物理页面动态分配。

**特权级、异常与服务接口。** OS 原理通过特权级隔离控制硬件资源访问，借助受控入口提供服务。本实验的 S 模式内核通过 `ecall` 请求 M 模式固件服务，体现了这一思想。但 SBI 调用是内核到固件的接口，不是用户程序调用操作系统的完整系统调用实现。本实验没有实现用户态陷入、参数检查和系统调用分发。

**设备抽象与分层设计。** OS 原理通过统一接口隐藏设备细节。本实验从 `cprintf`、格式化回调和控制台接口逐层到达 SBI 字符输出，展示了格式处理与底层输出的分离。这里主要复用了固件服务，没有实现完整 UART 驱动、中断输入或设备管理框架。

**运行时初始化与零初始化语义。** C 语言中静态存储期变量的初值要求依赖执行环境落实。普通应用通常由加载器及运行时提供支持，本实验则由内核主动调用 `memset` 清零。链接器提供的是区域边界符号，清零本身仍由 CPU 执行代码完成。

**调试与机器级证据。** OS 原理中的程序计数器、寄存器和指令执行，在本实验中可通过 GDB 直接观察。源代码的一个伪指令可能对应多条机器指令，优化和链接也会影响显示；判断状态必须结合真实地址及寄存器，不能只依赖源代码行号或 GDB 选取的符号名称。

### 6.2 OS 原理中重要但本实验未涉及的知识

1. **进程与线程管理：** 没有进程控制块、进程创建、阻塞唤醒、调度算法或上下文切换；最终循环不是调度器。
2. **虚拟内存与动态内存管理：** 没有建立分页映射、实现物理页分配、页故障处理、换页或堆分配器。
3. **中断与异常处理：** 虽然通过 SBI 使用异常机制，但没有建立内核自身完整的陷入入口、现场保存和中断分发，也没有实现时钟驱动的抢占。
4. **用户态及系统调用：** 没有用户程序装载、用户与内核地址空间隔离、用户栈、系统调用表及用户指针检查。
5. **文件系统与持久化：** 没有目录、文件、磁盘块管理、缓存或崩溃恢复；构建内核镜像不等同于实现文件系统。
6. **同步与并发：** 没有实际实现锁、信号量、条件变量，也没有验证多核并发、竞争条件及死锁处理。
7. **完整设备和资源管理：** 没有设备枚举、DMA、驱动框架、权限检查或资源回收。这些能力需要在后续实验中逐步补充。

### 6.3 AI 协作开发的经验

本次协作采取逐步操作、反馈真实结果、再解释现象的方式。AI 给出的预期需要由命令输出验证，例如栈大小用两个符号地址相减确认，尾调用用 `ra` 前后不变确认，无限循环用自跳转指令确认。

首次断点未命中时，单看 GDB 的 `Continuing` 容易误以为调试器卡死；同时检查 QEMU 的 `Next Address` 才找到了启动配置问题。因此排错需要综合固件日志和调试器状态，也需要注意教材环境与实际工具版本的差异。

只有出现 `(gdb)` 提示符时才输入下一条调试命令；目标程序持续运行时应先用 `Ctrl+C` 暂停。反汇编里的指令用于理解目标 CPU 的行为，实际单步应使用 GDB 的 `si`。记录失败过程和修复证据，比仅保留最终成功截图更有助于复现和解释实验。
