# Lab2 调试复现与尚需演示的部分

## 已完成：客体 GDB 验证

在工程目录执行：

```sh
make -j2
python3 tools/capture_mmu.py
```

需要 `gdb-multiarch`（含 Python）、QEMU，端口 1235 空闲。脚本会单独启动并关闭自己的 QEMU。GDB 文件位于 `tools/mmu.gdb`，观察分页前后 satp、根页表项，并动态查找 `kern_init` 序言中的 `sd` 指令、计算有效地址、单步执行、核对物理别名中的值。源码变化可能改变地址，脚本通过符号重新计算。

真实输出在 `verification/mmu-gdb.log`。这一步验证当前客体页表，不等于宿主机中单步执行 QEMU C 源码。

## 尚需演示：宿主机 GDB 调试 QEMU 源码

手册指定 QEMU 4.1.1；虚拟机实际安装的是 8.2.2。本次没有替换系统 QEMU。下面是补做源级演示的步骤，未执行部分不应在提交报告里写成实测。

1. 在独立源码/构建目录准备带调试符号的 QEMU 4.1.1，按该版本依赖配置 `--target-list=riscv64-softmmu --enable-debug` 并编译。旧版可能与较新的 Python/编译器依赖不兼容，保留失败日志再处理，不覆盖系统安装。无需 `sudo make install`。
2. 终端 1 在工程目录启动：

   ```sh
   make debug QEMU=/绝对路径/qemu-4.1.1/riscv64-softmmu/qemu-system-riscv64
   ```

3. 终端 2 用 `pgrep -af qemu-system-riscv64` 找到**这次调试进程**，用宿主机 `gdb /绝对路径/调试版qemu` 后执行 `attach PID`。如 attach 权限不足，使用符合本机权限设置的方式启动/附加该进程。
4. 终端 3 在工程目录用 RISC-V GDB 或 `gdb-multiarch bin/kernel` 连接 `target remote localhost:1234`。先让宿主机 GDB `continue`，否则客体 GDB 连接/命令会等待。

首次地址过滤可先用 `kern_init` 的虚拟地址，但若要观察数据访问，最好选 `tools/mmu.gdb` 找到的 `sd` 栈地址；本次为 `0xffffffffc0205ff8`。地址与重编译有关，应重新读取，不能照抄。

宿主机 GDB 中可参考：

```gdb
set pagination off
handle SIGPIPE nostop noprint pass
break riscv_cpu_tlb_fill if address == 0xffffffffc0205ff8
break get_physical_address if addr == 0xffffffffc0205ff8
continue
```

然后在客体 GDB 执行到选定存储指令。宿主机断住时记录 `bt`、`access_type`、`mmu_idx`、`env->satp`，单步进入翻译函数，查看 `base`、`idx`、`pte_addr`、`pte`、`ppn` 及返回的物理地址。静态函数能否设置断点受构建调试信息和优化影响，需要按实际符号与源码行定位。

本次是根层大页叶项，循环不应被描述成必然遍历三次。将页表项地址和结果与客体 GDB 的观察对照。

TLB 查询需要另看 `accel/tcg/cputlb.c` 的 `load_helper`、`store_helper`、`tlb_hit` 调用处，以及 `tcg/i386/tcg-target.inc.c` 的 `tcg_out_tlb_load` 生成路径；inline 函数可能需要按源码行设断点。不要把“未命中补表函数”当作“每次访问的入口”。第一次访问未必一定未命中，可通过选择新页面或在客体执行适当的 `sfence.vma` 后观察；不能仅凭没有触发慢路径断点就宣称查表失败。

SIGPIPE 设置用于避免宿主机 GDB 因相关通信信号反复打断；本次未执行省略该设置的对照实验，因此没有编造相应现象。

最后对比分页前后的路径：Bare/有效 M 模式的地址转换可以直通，但 QEMU 仍需定位宿主机 RAM/MMIO；软件 TLB 不只是对真实硬件页表 TLB 的逐项复制。提交时补入真实的宿主机断点回溯、翻译变量和命中/未命中现象截图。
